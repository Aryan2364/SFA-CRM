## 1. HOW TO USE THIS FILE

This section does not change between products. Leave it as written.

**Naming.** Every plan file is `plan-YYYY-MM-DD-HHMM.md` — four digit
year, two digit month, day, then a 24-hour time with **no colon**.
`plan-2026-08-31-1125.md`. Windows forbids a colon in a filename, and a
plan written on a Mac with `11:25` in its name cannot be checked out on
the machine this is built on. The date is when the plan was written, not
when the work happens.

**Supersession.** A plan is never edited into a new plan and never
deleted. When the plan changes materially, write a new file with a new
timestamp and leave the old one in place. The old file is the record of
what was believed at the time, which is the only thing that explains why
a decision was made. At the top of the superseded file add one line:

```
Superseded by plan-YYYY-MM-DD-HHMM.md on DD Mon YYYY.
```

**The pointer.** `plan.md` is two lines and nothing else. It is the only
file anyone has to know the name of:

```
Active plan: plan-YYYY-MM-DD-HHMM.md
Read that file before doing anything in this repository.
```

Update those two lines whenever a new plan supersedes the old one. If
`plan.md` points at a file that does not exist, every session starts by
guessing.

**⚠️ THE POINTER DOES NOT EXIST IN THIS REPOSITORY AND CANNOT.** See §4
item 1. This repo already contains `PLAN.md` — the migration record — and
Windows is case-insensitive, so `plan.md` and `PLAN.md` are one file.
Until that is resolved, the active plan is the newest `plan-*.md` by
timestamp. This is a known deviation from the rule above, recorded rather
than papered over.

**Order of reading.** `AGENTS.md` is the rulebook and outranks this file
on anything to do with design or build. This file is product state: what
is being built, what has been decided, and what is still open. Where they
appear to conflict, `AGENTS.md` wins and the conflict is a bug in this
file.

`AGENTS.md` lives at `D:\RGB_Software\rgb-kit-v2\AGENTS.md` — a sibling
repository, not inside this one. There is no copy here and one must not be
made; a second copy drifts.

## 2. PRODUCT

RGB SFA is a multi-tenant sales force automation admin panel: field sales
staff file daily activity, expenses, orders and leads against a weekly
plan, and their managers review, approve and score that work. It replaces
spreadsheet-and-WhatsApp reporting. Indian client, so `AGENTS.md` §18
applies as written — DD/MM/YYYY, lakh/crore digit grouping, `₹`.

This is **an existing product in production being brought into line with
the kit**, not a new build from it. That inverts the usual §0.1 order: the
screens exist and the token layer does not.

**This product goes to the same client who uses Sadbhavna, built from the
same kit. The same people use both.** Colour differs deliberately — RGB
SFA is indigo, and that is the only intended difference. Everything else
follows `AGENTS.md`, which means the two products match automatically
without either being compared to the other.

**That raises the standard, and it is the reason the scope changed.**
Anything left non-compliant does not read as a rule violation in
isolation. It reads as an inconsistency between two products one person
uses in the same week — a button that is a different height, a date in a
different format, an empty state that says "No data" in one product and
offers an action in the other. The subset that would have been acceptable
for a product with no sibling is not acceptable here.

Brand colour: deep indigo `#3D3A6E`. See §3.

   was copied from the other. Comparing code would propagate Sadbhavna's
   own drift into this product and make its bugs this product's bugs.
   `AGENTS.md` is the specification; `D:\RGB_Software\rgb-kit-v2\app\kitchen-sink\page.tsx`

4. **Neutrals and status colours come from the kit unchanged** —
   `AGENTS.md` §2.3 and §2.4. Status colours do not move when the brand

     component and the kitchen sink, rebuild the behaviour — not as files.

6. **The API layer is out of this work entirely.** 115 routes, 7,514
   lines, no UI. The retrofit surface is 51 `.tsx` files / ~12,400 lines,
   not the repo's 21,184.

7. **No second charting library.** `AGENTS.md` §21 names recharts, already
   a dependency here at 3.7.0.

## 8. WHAT A FAST MODEL WILL GET WRONG

1. **Copying the kit's `globals.css` or its components verbatim.** Both
   are Tailwind 4 / React 19 / Radix. See §3 item 5. `globals.css` will
   appear to work — Tailwind 3 ignores `@theme inline` silently — and
   every token will be undefined.
2. **Comparing against the Sadbhavna codebase.** Forbidden, §3 item 3.
   The specification is `AGENTS.md`; the reference is the kitchen sink.
3. **Changing `--primary` alone.** All seven move together, or five shades
   keep the old brand. `AGENTS.md` §2.2.
4. **Mapping `text-gray-400` to `text-muted` as a like-for-like.** It is
   not. See §11 — a contrast fix that visibly changes 200 call sites, and
   that is intended.
5. **Touching `src/app/api/`.** 115 routes, no UI. The one exception is
   the email template in `auth/forgot-password/route.ts`, an HTML string,
   not JSX — and out of scope anyway (§13).
6. **Treating `w-4.5` / `h-4.5` as valid.** 28 occurrences in
   `masters/page.tsx`. Not in Tailwind 3's scale, empty `extend`, so they
   compile to nothing and those icons are unsized today.
7. **Building Add and Edit as separate forms.** `AGENTS.md` §4 rule 1.
   This codebase already gets this right — every master page uses one
   modal with an `editing` state. Do not "improve" it into two files.

The absence of `button` and `input` is what produced the 130 raw
`<button>` and 92 raw `<input>` in screens. They are a symptom, not the
disease.

**`lib/utils.ts` and the `cn()` trap, which applies here too.** §4.1
records that `cn()` is not plain tailwind-merge: it is extended with the
type-scale token names. tailwind-merge treats any unrecognised `text-*`
class as a text colour, and the type scale lives in the `text-*` namespace
too — so `cn("text-label", "text-text-secondary")` classified both as
colours, kept the last, and dropped the font size silently. Every label
rendered at the inherited size with no error anywhere. **Anything added to
the type scale is added to the `cn()` extension in the same commit.**
Related: a type-scale token must never share a name with a colour token —
`--text-card` collided with `--color-card` and card titles rendered white
on white, which is why the kit's token is `--text-card-heading`.

This product has no `cn()` at all today, and no `clsx`, `classnames`,
`tailwind-merge` or `cva` in `package.json`. Phase 1 introduces it with
the extension already in place, rather than discovering the trap later.
