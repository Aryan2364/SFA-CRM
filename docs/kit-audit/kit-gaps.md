# Kit gaps — owner review

(Carried forward from `foundation.md`'s own KIT GAPS section; add to this list, do not fix by editing the kit.)

- [globals.css] `--on-brand-accent` is documented by the kit as an explicit, measured pick per brand (sec 11.7, "primary's hue, 45% saturation, 72% lightness because this brand is dark") rather than a derivation — but this app has no sign-in screen yet to measure against. Added as a `color-mix` derivation instead, flagged for ratification once a sign-in screen needs it, the same way this file already flags `--primary-subtle-hover/-pressed`. The kit doesn't document a safe fallback for "brand needs this token before the screen that would let you measure it exists."
- [permission-tooltip] The kit's `DeniedReason` (phone branch) opens on tap and toggles on a second tap, closing on the next tap anywhere — this depends on `useLayout()` and the surrounding `Tooltip`'s `disabledReason` prop, both present in this app's `lib/layout.ts` already, so no gap here. Noting only that this wiring was previously absent app-side (pre-sync `permission-tooltip.tsx` used a fixed `allowed: boolean`, no phone affordance at all) — worth the kit calling out explicitly that a product porting this component for the first time needs `tooltip.tsx` synced in the SAME commit, since `disabledReason` doesn't exist on an older `tooltip.tsx`.
- [multi-select / inline-choice] Both kit components assume `select.tsx` exports `usePhoneTriggerProps` and `searchable-select.tsx` exports `useSearchPicker`. Neither is documented anywhere as a required co-dependency — a product that syncs `multi-select.tsx` without first syncing `select.tsx`/`searchable-select.tsx` gets a silent missing-export TypeScript error with no pointer back to "sync select.tsx first." Worth a note in the kit's own component-level docs (or a comment at the top of multi-select.tsx) naming the exact exports it needs.
- [comment-box] RESOLVED Wave 8B — ported `content-area.tsx` and the full `keyboard-shortcuts.tsx` (all its own deps — `command.tsx`, `dialog.tsx`, `table.tsx`, `sonner.tsx` — already existed from earlier waves; only `progress-bar.tsx` was missing, also ported). `comment-box.tsx` itself is now byte-identical and compiles. The underlying complaint stands as kit feedback: pulling the whole shortcuts dialog system in for one keydown helper (`enterSends`) is still disproportionate, even though this app absorbed the cost. Worth the kit still splitting `enterSends`/`ctrlEnterSaves`/`searchBoxKeys` into their own lib file.
- [draft-banner] Needs `formatDateTime`/`formatTime` in `lib/format.ts` and a `lib/drafts.ts` module (`Draft`/`DraftValues` types plus persistence). The kit ships these as part of its own `lib/`, but doesn't flag anywhere that `draft-banner.tsx` is non-functional without them — same class of issue as the `multi-select` note above: a component file by itself doesn't say what else it needs.
- [unsaved-changes] Needs `whenLayersSettled` exported from `sheet.tsx`. Same undocumented-co-dependency pattern.
- [`src/lib/permissions.ts`] carried over from `foundation.md`: the kit ships a same-named file that is NOT meant to be synced over the app's real RBAC logic (app's reads `role_permissions`/`checkPermission`/`getDataScope` per this repo's CLAUDE.md; kit's is a toy/demo). Nothing in the kit's docs flags this file as "replace the shape, never the logic" the way this repo's own CLAUDE.md does. Worth the kit adding an explicit note distinguishing its `lib/` demo helpers from files a real app must keep product-owned.
- [bottom-bar/phone contract] Carried over: large and all-or-nothing, no incremental-adoption guidance for a product (like this one) that already shipped a non-kit phone layer before adopting the token contract.
- [badge/empty-state] `EmptyState`'s action button has no `actionDisabledReason`/permission-tooltip support — a product following the kit's own permission rules (§26: a disabled action is shown with a reason, never hidden) has no documented way to apply that to the one action button `EmptyState` itself renders. App had this working pre-sync (`actionDisabledReason` prop); dropped on sync, filed as a regression to fix either in the kit or by wrapping the action externally.
- [searchable-select] No headed-group support (`SearchableSelectGroup`) — second real call site found this wave (`daily-activity/add-meeting-dialog.tsx`, Accounts vs Contacts) wanting the same thing `foundation.md`'s `multi-select.tsx`/`inline-choice.tsx` note already flagged for `select.tsx`. Worked around by flattening groups into one list with the group folded into the label text; a real grouped-list affordance in `searchable-select.tsx`/`command.tsx` would serve both.
- [ref-as-prop / React version] Several kit files assume React 19's "ref is an ordinary prop, always mutable" model (`textarea.tsx`, `sheet.tsx`, `alert-dialog.tsx`, `input-group.tsx`'s `InputGroupTextarea`). This app runs React 18.3, where a destructured `ref` prop is typed as the legacy `string | RefObject<T> | RefCallback<T>` union and `RefObject<T>.current` is read-only — every one of these files failed to typecheck unmodified. Patched locally with type overrides/casts (see changes.md); every future kit file sync that destructures `ref` as a prop will hit the same wall until the app upgrades to React 19. Worth the kit either noting a React-18 compatibility shim pattern, or flagging React 19 as a hard prerequisite up front.
- [sheet/app-bar] `sheet.tsx`'s full-screen phone-sheet header depends on `components/shell/app-bar.tsx` (`PhoneAppBar`), which itself depends on `lib/back.ts` and `components/shell/progress-bar.tsx` — neither ported. A minimal local shim (`src/components/shell/app-bar.tsx`, not from the kit) was written supporting only the 4 props `sheet.tsx` actually passes, so `select`/`dialog`/`popover`/`dropdown-menu`/`searchable-select` (which all need `sheet.tsx` for `SheetBody`/`useSheetStep`/etc.) could compile without pulling in the whole back-navigation + progress-bar subsystem. This is the same "a component's own file doesn't say what else it needs" pattern `foundation.md` already flagged for `multi-select`/`comment-box`/`draft-banner`/`unsaved-changes` — `sheet.tsx` belongs on that list too.
- [approval-select] RESOLVED Wave 8B — ported `approval-select.tsx` byte-identical. Added `Noun`/`PhoneListSelection` as additive, type-only exports to the app's reduced `phone-list.tsx` (structurally identical to what it already used inline for `noun`; `PhoneListSelection` has no runtime consumer yet — this file's `PhoneList` still has no select-mode rendering) and a no-op-safe `useAppBarOverride` stand-in to the app's `shell/app-bar.tsx` shim (its context has no provider anywhere, so the hook is always inert). The component compiles and is available, but is NOT wired into any list — bulk approve/reject select mode is a new product feature, not a safe additive change, and needs: (1) `PhoneList`'s rendering actually taking a `selection` prop and drawing tick boxes, and (2) a real `AppBarProvider`/override wired into `phone-app-bar.tsx`/`phone-shell.tsx` so "5 selected" actually shows. Both left for a product-feature wave.
- [notification-permission-sheet] RESOLVED Wave 8B — ported `notification-permission-sheet.tsx`, `lib/install.ts`, `lib/push.ts` byte-identical (all pure client-side; no backend added). `lib/install-settings.ts` already existed with the app's brand values in the exact shape these three need, so nothing to merge there. `PUSH_CONFIGURED` is false (no `NEXT_PUBLIC_VAPID_PUBLIC_KEY` set anywhere), so push degrades to "not configured" exactly as the kit intends for a product that hasn't set one up — nothing was offered or mounted. To actually enable push, the owner needs: a VAPID key pair, a push-subscription table + API routes to store/delete it per person, a service worker (`public/sw.js` + `public/sw-push.js`, registered nowhere yet) and a send-time dependency (e.g. `web-push`) on whatever backend sends `{title, body, url, tag}`. None of that was built, per the brief.
- [banner/dismissals] `banner.tsx`'s `BannerClose`/`useBannerDismissal` need `BannerDismissalsProvider` (reading `lib/banner-dismissals.server.ts`'s `getInitialBannerDismissals()`) mounted in the root layout to avoid a first-paint flash. Ported the component and both lib files this wave (Wave 1c) since the cookie scheme needs no backend, but did not mount the provider anywhere, since no page yet calls `useBannerDismissal` — the kit doesn't flag that `banner.tsx` is inert (no first-paint correctness) until a product's root layout wires the provider in, the same "file doesn't say what it needs" pattern as above.
- [dialog.tsx] An irreversible action with a form body (deal-status.tsx's Won/Lost close, needing a reason + stage) can't use alert-dialog.tsx (no form body) and dialog.tsx closes on Escape/backdrop (kit section 24 rule 3) — wrong for a confirmation. Worked around at the call site by checking `eventDetails.reason` in `onOpenChange` (Base UI's dialog root hands back a cancelable change-event with a `reason` of `escape-key`/`outside-press`/etc.) and calling `eventDetails.cancel()` for those two reasons, letting only an explicit DialogClose/Cancel/action close it. dialog.tsx itself exposes no `preventDismiss`-style prop, so every future form-body confirmation will need the same per-call-site workaround until the kit adds one.
- [RemarksPanel/remark-thread] RESOLVED Wave 8B (RemarksPanel only) — comment-box.tsx's prerequisites are now ported (see above), and `RemarksPanel.tsx`'s composer was swapped to `CommentBox`: same `POST /api/remarks` call, Enter-to-send on desktop replacing Ctrl+Enter-only. `src/components/remark-thread.tsx` (`RemarkThread`) was deliberately left as a hand-rolled textarea: it is one section embedded among several on a bigger page (review/[userId]'s tabs; a deal/meeting's detail page via `conversation-thread-sheet.tsx`), never the page's whole purpose, and `CommentBox`'s phone behaviour is a page-bottom *fixed* bar meant for a screen that IS one thread — using it inline would wrongly pin a fixed element over unrelated page content below it on phone. This is a real kit gap: comment-box.tsx has no "inline, non-fixed" mode for a thread that's only one section of a larger page (its non-phone branch is already a plain non-fixed row; only the phone branch assumes full-screen ownership). Worth the kit adding an `inline` prop that skips the ghost/ ActionBar fixed-bottom contract on phone too.
- [masters] `templates/list-page.tsx` has no drag-to-reorder capability, so migrating a soft-deleted master that supported manual `sort_order` ordering under the legacy `CrudPage` (industries, contact-types, expense-categories, todo-unmet-reasons, lead-temperatures, reason-for-loss) onto `ListPage` drops manual reordering — rows now render in whatever order `sort_order` was last left in, with no way to change it from the UI. Needs either a `ListPage` reorder prop/mode, or an explicit product decision that masters are alphabetical/creation-order going forward. Logged in Wave 2A's `changes.md` entry.
- [badge.tsx] The closed 4-colour status system (neutral/success/warning/danger) has no "info"/cool row for a status that is neither good, bad, cautionary nor simply inactive — `masters/lead-temperatures`' "Cold" had to map onto `neutral` for lack of a better fit. Same gap class as the existing AVATAR_COLORS note for access-control.
- [access-control] Access Control screen set (Roles & Permissions / Reporting Schema / Org Chart) does not match kit §40.1's 4-tab prescription (Roles, People, What they can do, History) — logged by the audit, left unrestructured per Wave 2C instructions. Needs an explicit owner decision: adopt the 4-tab structure (folding Org Chart/Reporting Schema elsewhere) or record this as a permanent exception.
- [access-control] Pre-emptive "N people have this role" disable on role delete not implemented — the people-count only exists server-side in the DELETE route's 409 response body, not exposed ahead of the attempt. Needs a small API change (e.g. a people-count field on the roles list endpoint) before the UI can show it before the click.
- [access-control / superadmin companies] No kit token exists for "N distinct-but-harmonious colours for initials/classification" — access-control's `AVATAR_COLORS` array and superadmin's `CLS_STYLES` usage-analytics breakdown colours are both closed small-N palettes with no status-token equivalent. Left as raw Tailwind in both places; needs either a small dedicated token set agreed in globals.css or an explicit written exception.
- [review/team-member-table, review/team, review/weekly] Raw `<table>` markup not yet converted to kit `table.tsx`/`col-*` tokens — sortable, multi-column numeric tables, more work than Wave 2C's remaining budget allowed. Flag for a follow-up wave.

- [masters/reorder] Kit has no list-reorder component (board.tsx's drag/keyboard reorder is card-board-specific, not a table-row pattern) — restored the Wave 2A regression (drag-to-reorder dropped when industries/contact-types/expense-categories/todo-unmet-reasons/lead-temperatures/reason-for-loss moved off legacy `CrudPage` onto `MasterNamePage`/`ListPage`) by having `MasterNamePage` pass `ListPage`'s existing `renderData` escape hatch a `kit Table` it renders itself: a `GripVerticalIcon` HTML5-draggable handle per row, plus `ChevronUpIcon`/`ChevronDownIcon` buttons as the keyboard-accessible fallback (native drag-and-drop has none — kit §39). Persists the same way the legacy `useCrud.reorder()` did: one `PUT .../[id]` per row whose `sort_order` changed, same body shape the route already accepts, optimistic reorder with rollback+toast on failure. `Wave 3A — masters finish` in changes.md has the full file list.

- [push / VAPID key at runtime] `lib/push.ts` read `NEXT_PUBLIC_VAPID_PUBLIC_KEY`; this project forbids every `NEXT_PUBLIC_` variable, so the key is fetched at runtime from `GET /api/push/vapid-public-key` and cached in module scope (`ready` is false until the first answer; a failed request is retried and reads as "not set up" meanwhile). The kit should offer a runtime-key variant. — FRONTEND_RULES_PHONE 41.12 rule 4, push.ts — PORT NOTE in the file.
