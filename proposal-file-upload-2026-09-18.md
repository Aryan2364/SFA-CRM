## Component API

```tsx
type UploadedFile = {
  id: string            // server row id; absent while the upload is in flight
  name: string
  size: number
  contentType: string
  url: string           // app-relative, re-authorises on every fetch. Never an R2 address.
  state: 'uploading' | 'done' | 'failed'
  progress?: number     // 0-100, only while uploading
  error?: string        // the server's sentence, shown on the row
}

type FileUploadProps = {
  files: UploadedFile[]
  accept: string            // e.g. 'application/pdf,image/jpeg,image/png'
  acceptHint: string        // the §29 sentence, e.g. 'PDF, JPG or PNG. Up to 10 MB.'
  maxBytes: number
  onUpload: (file: File, onProgress: (pct: number) => void) => Promise<UploadedFile>
  onRemove?: (file: UploadedFile) => Promise<void>   // omitted => no remove button
  onRetry?: (file: UploadedFile) => void
  disabled?: boolean
  disabledReason?: string   // §26: wrapped in PermissionTooltip, never a silent disable
}
```

The component owns the drop zone, the row list, progress and the failed-row treatment.
It owns no network call: `onUpload` is the caller's, so the kit never learns an endpoint
shape. The caller passes `acceptHint` and `maxBytes` rather than the component inventing
them — sfacrm already exports both from
`src/app/api/deals/[id]/attachments/_shape.ts` as `ACCEPT_HINT` and `MAX_SIZE`, so the
sentence above the drop zone and the sentence in the 400 are generated from one constant
and cannot drift.

## How it meets §29

| §29 requirement | How |
|---|---|
| Bordered drop zone, browse button inside, drag **and** click both work | The zone is a `<label>` wrapping a visually-hidden `<input type=file>`, so click and keyboard work with no handler; `onDragOver`/`onDrop` add the drag path. |
| Types and cap stated visibly, before the user tries | `acceptHint` renders above the zone, always, not as a tooltip or a placeholder. |
| Each file is a row: name, size, remove, download | Exactly those four, in that order. Download is the row's `url`. |
| Long names truncate per §8 | Name cell uses the §8 single-line truncation with the full name as its title. |
| Progress on the row, not a page overlay | A track along the row's bottom edge, driven by the `onProgress` callback. |
| A failed upload stays, in the danger colour, with Retry | `state: 'failed'` keeps the row, colours it `--danger`, swaps the download link for Retry. It never vanishes. |
| Images preview, other types get a file-type icon | `contentType` starting `image/` renders a 32px thumbnail from the row `url`; PDF gets the §23.1 file icon. |
| Removing a saved file follows §15 | `onRemove` on a row with an `id` opens `AlertDialog`; a row still uploading has no `id` and is dropped without a prompt. |

Two rules from elsewhere that this component must not be allowed to miss:

- **§26** — a caller without `deals:edit` gets `disabled` plus `disabledReason`, wrapped
  in `PermissionTooltip`. The control is visible and explains itself; it is never
  silently inert, and never simply absent, because absence is indistinguishable from a
  bug.
- **§7.1** — a rejected file is an inline error on its own row, not a toast. The user is
  looking at the row.
